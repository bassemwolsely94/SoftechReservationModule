## 3. INVESTIGATION REQUIRED (Phase 1 — do before dependent builds)

### Track BATCH-CONSTRAINT — mandatory-batch master flag (directive §12-16, §65)
Goal: find the authoritative SOFTECH `items` (or config) column that means "batch/expiry selection required"
(distinct from "batches happen to exist"). Method: read-only column diff of a known batch-required item vs a
known optional item, then confirm native POS behavior for both. Then sync → `catalog.Item` → POS batch matrix
(CASE 1-5). **Owner evidence needed:** name one item where batch selection is mandatory and one where it is
optional (+ a screenshot of each item-master row if possible).

### ✅ Track BATCH-CONSTRAINT — DECODED 2026-09-13
**Authoritative field = `SOFTECHDB9.dbo.items.itempartno`** (numeric boolean; «رقم القطعة أو الباتش»).
`1` = batch/expiry selection MANDATORY at POS; `0` = optional. SPARSE: only **9 items** master-wide are `=1`
(51,711 `=0`) — owner-confirmed set incl. Entresto 50/200mg (119729/120049/120468) and even a non-medicine
coupon (118639 استحقاق كوبون), which proves it's a deliberate master flag, not "is a medicine". Orthogonal to
stockable (`itemtrans` — all 9 are `itemtrans='1'`). Name aligns with the batch-number sale-line column `item_partno`.
Method: full items-master column diff of the 4 owner-named required items vs contrast items → the ONLY short-valued
column with req all-`1` / contrast all-`0`. **BUILT (increment 1, data foundation):** `catalog.Item.batch_required`
(mig catalog/0036) ← synced from `items.itempartno` (sybase_queries col 39 + tasks.py parse) + exposed on the item
serializer + filterset (`?batch_required=1`) + backfilled (9 items) + lights the 📦 BatchBadge on ProductCard.
**STILL OPEN (increment 2 = batch matrix CASE 1-5 enforcement):** requiring selection before push + the CASE-2
question (single-batch: auto-select vs confirm?) needs native-POS confirmation — touches writer/validation → stop-and-ask.

### ✅ Track BATCH-CONSTRAINT — increment 2 (matrix enforcement) BUILT 2026-09-13 (owner-approved)
Owner confirmed CASE 2 ("single available batch → SOFTECH auto-selects it") and said "finish Wave 2". The full
CASE 1-5 matrix now lives as a **pure, tested, server-side decision** — `batch_availability.batch_action(batches,
batch_required, stockable)` returns one of `plain` / `reserve` / `auto_select` / `must_select` / `optional`
(backend owns the rule, CLAUDE.md §7). Surfaced from `batch_availability_view` as `batch_action` (+ `batch_required`).
POS (`usePosOrder.addItem`) consumes the verdict (derived fallback for older backend): CASE 2 auto-adds the line
bound to the single batch; CASE 1 opens the batch modal flagged `mandatory` → `confirmBatchPick` refuses a
batch-less confirm and the «إضافة» button is disabled until a real pick; CASE 3 → حجز (unchanged); CASE 4/5
non-mandatory keep the optional FEFO helper. Backstop: `clientValidate` blocks push of any `batch_required` line
that reaches checkout without a batchno (guards the no-branch / read-error add-paths). Modal shows a red
«رقم القطعة أو الباتش — إلزامى» notice + BatchBadge. NO writer change, NO SOFTECH write, NO doc-number touch —
purely which line the cashier builds. Tests: `test_pos_batch_availability.BatchMatrixTests` (5 cases, green);
frontend build clean.

### ✅ Track POS-AUDIT — DECODED 2026-09-14
Owner supplied the report screenshot («سجل المبيعات الغير مخزنة» = log of NON-STORED sales, by branch+period,
grouped by seller, columns customer/item/qty/public-price/sale-price/time/amount, with qty=0 rows mixed in) and
confirmed it records **items selected but not sold** (browsed / price-checked / removed before save). Read-only
probe (branch 170; HQ 192.168.1.8 was down) DECODED the source: **SOFTECH table `pos_cancel`** (`pos_cancel_old`
= archive). `stktrans` was ruled out — it has ZERO `transqty=0` rows on any doccode; `pos_cancel` had 14,253 of
19,488 recent rows at `transqty=0`. Column map: `custcode`→customer · `itemcode`+`mitemname`→item · `transqty`→qty
· `itemsaleprice`→بيع للجمهور · `transprice`→سعر البيع · `transprice_total`→amount · `trans_time`→time ·
`usercode`→seller group · `doccode` 115=would-be sale / 30=would-be return. Meaning: every POS line entered then
NOT committed to `stktrans` is logged here (`transqty>0`=priced line cancelled; `transqty=0`=item selected/cleared
w/o qty). **Value:** lost-sale signal (asked-for-not-sold → demand/procurement) + per-cashier cancellation/abuse
audit; value-at-risk = Σ `transprice_total` of qty>0 rows.

**✅ BUILT increment 1 — live read-only lost-sales view (2026-09-14, owner picked "both: live now, sync later"):**

## 4. Sequenced build waves (each = one approved batch, reuse-mapped)

Order chosen to unblock the most with least risk; every wave: backend-first where rules live → wire frontend →
tests → build → no regressions → doc update.

1. **Design System foundation** (NEW, frontend-only, safe) — the semantic layer + primitives above. Unblocks all visual work.
2. **Batch investigation + hardening** (INVESTIGATE→EXTEND) — Track BATCH-CONSTRAINT, then `catalog.Item` sync + POS batch matrix + `BatchBadge`/visual FEFO allocator (reuse `apps/batches`).
3. **POS-AUDIT investigation** (INVESTIGATE) + extend `apps/audit` POS event stream (permanent, separate from SOFTECH).
4. **Visual POS pass** (EXTEND) — ProductCard 2.0, branch-stock heatmap pills, contextual action bar, adaptive WorkflowBar, actionable errors/empty states, always-on customer mini-strip. Reuse CustomerDrawer/ItemSearchWidget.
5. **Fulfillment-at-point-of-need** (EXTEND) — network stock → one-click transfer(`transfers`)/reserve(`reservations`)/demand(`apps/demand`); "recover sale" when demand/transfer/reservation becomes fulfillable.
6. **Next-Best-Action + Smart Basket + refill radar** (EXTEND) — evolve `workflow.next`; reuse `recommendations`/`offers`/`chronic`.
7. **Omnichannel** (EXTEND) — call screen-pop (`pbx`), WhatsApp→draft (`whatsapp`/`omni`), digital receipt.
8. **Exception Center + leakage/telemetry** (EXTEND) — aggregate exceptions; combine `apps/audit` telemetry with (once decoded) SOFTECH anomaly data for manager review.

**Do NOT start any wave touching pricing/discount/payment/checkout or a SOFTECH write without the explicit
stop-and-ask gate (CLAUDE.md).** Waves 1, 4 (visual only), and the investigations are safe to proceed on approval.

### ✅ WAVE 3 — POS-AUDIT (increment 3: WRITE our selections INTO pos_cancel) BUILT 2026-09-15 (gated OFF)
Owner directive: feed OUR POS item-selections into SOFTECH `pos_cancel` the same way the native POS does, batched
every few hours. `pos_cancel` is an activity **log** (no stock/document/money/e-invoice) — lower risk than the
pending-sales writeback, but built with the same discipline (flag OFF, dry-run first, never double-post).
Owner decisions: **log every add, EXCLUDE items that became a sale**; log **both** qty>0 and qty=0 (mirror native).
**Capture:** `PosSelectionEvent` (mig pos_orders/0014) + `POST /pos-orders/selection-events/` (batch ingest,
server-authoritative attribution); frontend `usePosOrder` emits on add/remove (buffered, debounced, fire-and-forget),
correlated to the eventual order via `client_token` (== cart token). **Writer:** `pos_cancel_writer.write_pos_cancel_batch`
— suppresses adds whose cart reached a real SOFTECH sale (pushing/pushed/settled) containing the item; writes native
12-col rows to each branch node via the writer's inline-literal insert; **idempotent without a PK** by claim-before-write /
un-claim-on-failure (can under-post, never double-post). Gated by `settings.POS_CANCEL_WRITE_ENABLED` (default False →
dry-run), command `write_pos_cancel`, scheduled every 3h (no-op while OFF). Tests `test_pos_cancel_writer` (12) green;
dry-run verified native-exact rows. **Before go-live:** owner reviews dry-run rows + confirms the `custcode` mapping,
then flips the flag. (Also fixed a pre-existing NameError in `return_lookup`.)
